push の前に毎回セキュリティ診断をしています。その観点を、重複や漏れがないように 9 つの区分に分けました。この記事では、区分ごとに **何を確認するか** を概要レベルでまとめます。

## 全体像

| # | 区分 | ひとことで |
|---|---|---|
| A | 入力→出力（注入） | 外から来た値が、危険な場所で「命令」として解釈されないか |
| B | 認証・セッション | 本人確認と、ログイン状態の維持は安全か |
| C | 認可・API | ログインした人が、許可された操作だけをできるか |
| D | ブラウザ境界 | ブラウザの防御機能を正しく使えているか |
| E | ビジネスロジック | 正しい値で、正しくない操作ができてしまわないか |
| F | 情報漏えい | 見せるべきでない情報が外に出ていないか |
| G | サプライチェーン | 自分が書いていないコード（依存ライブラリや CI）は安全か |
| H | デプロイ・設定 | 本番環境の設定や配信物に不備がないか |
| I | ログ・監視 | 問題が起きたときに気づけるか、ログ自体が漏えい源になっていないか |

## A. 入力→出力（注入）

外部から届く値（フォーム、URL、ヘッダー、JSON、ファイル、外部 API の応答）が、どこで使われるかを追います。

- **XSS**: HTML に出力するときにエスケープされているか。エスケープを無効にする書き方をしていないか。リンクの URL に `javascript:` が入り込まないか
- **SQL インジェクション**: SQL は文字列連結ではなく、パラメータ化して組み立てているか
- **OS コマンド・テンプレート・パストラバーサル**: 入力値がシェルのコマンド、テンプレート、ファイルパスとして解釈されないか
- **入力値の検証**: 「許可する値」を仕様から決め、それ以外を拒否しているか
- **ファイルアップロード**: ファイル名や Content-Type を信用していないか。保存先と配信方法は安全か
- **SSRF**: 利用者が指定した接続先へ、サーバーからリクエストを送っていないか

## B. 認証・セッション

- パスワードは安全な方式でハッシュ化して保存しているか
- ログインやパスワードリセットの応答の違いから、アカウントの有無が分からないか
- 総当たりを防ぐ試行回数の制限はあるか。MFA に対応しているか
- Cookie に `Secure` `HttpOnly` `SameSite` を付けているか
- ログイン時にセッション ID を作り直しているか。ログアウトや有効期限でセッションを無効にしているか

## C. 認可・API

- 「自分のデータか」を、オブジェクトごとにサーバー側で確認しているか（IDOR の防止）
- 一般ユーザーが管理機能を使えないか
- 権限は「許可したものだけ通す（デフォルト拒否）」になっているか
- API が返す項目・受け取る項目を明示しているか。処理量に上限があるか

## D. ブラウザ境界

- **CSRF**: 状態を変えるリクエストで、トークンなどによる検証をしているか
- **セキュリティヘッダー**: CSP、`X-Content-Type-Options`、`Referrer-Policy`、`Permissions-Policy`、HSTS、iframe への埋め込み制限を設定しているか
- **CORS**: 許可するオリジンを完全一致で指定しているか。リクエストの Origin をそのまま返していないか
- **クライアント側の処理**: `innerHTML` や `eval` に外部の値を渡していないか。秘密情報を Web Storage に置いていないか

## E. ビジネスロジック

- 守るべき条件（在庫がマイナスにならない、など）が、サーバー側で保たれているか
- 手順の飛ばし・並べ替え・二重送信で、想定外の状態にならないか
- 同時に実行されたとき（競合状態）にも正しく動くか

## F. 情報漏えい

- トークン・鍵・`.env` をリポジトリや配信物に含めていないか
- ソースマップや詳細なエラーメッセージを、本番で公開していないか
- ヘッダーなどからサーバーやライブラリのバージョンが分からないか
- 必要以上の個人情報や内部情報を返していないか

## G. サプライチェーン

- 依存ライブラリに既知の脆弱性（High 以上）がないか
- lock file をコミットして、同じ依存を再現できるか
- 新しく追加した依存の名前と配布元は正しいか（なりすましパッケージでないか）
- CI の権限は最小か。外部 Action はバージョンを固定しているか

## H. デプロイ・設定

- 秘密情報は Secrets や環境変数で管理しているか
- 配信物に不要なファイル（設定やバックアップなど）が含まれていないか
- 404 やエラーのときの挙動は意図どおりか
- 本番用の設定（デバッグの無効化など）になっているか

## I. ログ・監視

- ログにパスワードやトークンなどの機密情報を出していないか
- デプロイの失敗や不審な操作に気づける仕組みがあるか

## 判定の考え方

- 各区分を **OK / NG / N/A（理由）** で判定し、該当しない区分も「なぜ該当しないか」を残します。
- 「確認できなかった」と「問題がなかった」は区別します。
- 未修正の Critical・High が1つでもあれば **FAIL** とし、push しません。

区分ごとの具体的な確認手順は、別の記事で掘り下げる予定です。
