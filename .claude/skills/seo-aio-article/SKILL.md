# SEO・AIO を考えた記事の書き方

検索エンジンは「どの検索語に答えるページか」を、AI は「どの一文をそのまま引用できるか」を見ている。どちらにも効くのは、**問いに対する答えを、具体的に、一文ずつ自立した形で、構造化して書く**こと。この skill はその手順とチェックリスト。

記事ページには、目次（`##` が 3 つ以上のとき、`##` と `###` から自動生成）・著者紹介・関連記事（タグの重なり順）が自動で付く。目次に出るので、見出しは単独で読んで意味が通るように書く。

サイト側の仕組み（canonical・OGP・JSON-LD・パンくず・サイトマップ・RSS・`robots.txt`・`llms.txt`・`llms-full.txt`）はテンプレートが自動で出すので、記事では **frontmatter と本文** だけに集中する。トップや一覧ページの文言を変えるときも、同じ考え方（タイトルの前半に主キーワード、description の 1 文目で答え、構造化データと食い違わない）で書く。

## 0. 書く前に決める

1. **想定読者と検索語**: 誰が、どんな言葉で探すか。主キーワード 1 つと関連語 2〜3 個を決める（例: 主「Claude Code コスト 表示」、関連「mod」「プラグイン」「モデル 警告」）
2. **この記事が答える問い**: 「〜するには？」「〜とは？」「〜で何を確認する？」を 1 文で書けるか。書けなければ記事の範囲が広すぎる
3. **slug（ファイル名）**: 英小文字とハイフン。主キーワードを入れる（`claude-code-mod-session-cost.md`）。公開後は変えない（URL が変わるため）

## 1. frontmatter

```yaml
---
title: 主キーワードを前に寄せた、何が得られるか分かる題（全角 32 字前後まで）
date: 2026-11-16          # 公開日
updated: 2026-11-20       # 内容を更新したときだけ。dateModified とサイトマップに使われる
description: 1 文目で答えを言い切る。何を・どうやって・何が載っているか。全角 80〜120 字
tags: [Claude Code, TypeScript]   # 既存タグの表記に合わせる（/search/ のタグ一覧で確認）
summary:                  # 冒頭の「この記事の要点」。3 つ前後。各項目は単独で意味が通る 1 文
  - …
faq:                      # 任意。本文で答えている質問だけ。末尾の「よくある質問」と FAQPage 構造化データになる
  - q: 読者が実際に打ちそうな疑問文
    a: 1〜3 文で完結する答え
---
```

- `title`: 検索結果では後ろが切れる。主キーワードと「何が得られるか」を前半に置く。「〜について」「〜の話」のようなぼかした題にしない
- `description`: 検索結果の説明文と、AI が最初に読む要約になる。「〜を整理した」より「〜は A・B・C の 3 つ」のように中身を書く
- `summary` / `faq` は **プレーンテキスト**（Markdown・HTML は書かない。そのまま文字として表示される）
- `faq` は本文と食い違わないこと。本文にない情報を足さない

## 2. 本文の構成

- **冒頭の段落（見出しの前）で結論を言う**: 「〜すると〜できる」「〜は〜の 3 つ」。前提となるバージョン・確認した時点（「2026 年 11 月時点」）もここに入れる
- **見出しは中身が分かる文に**: 「概要」「詳細」ではなく「課題：〜が見えない」「3. claude plugin validate で検証する」。ユーザーが構成を指定したときは、その見出しの語を先頭に残して補う（例: 「課題：〜」）
- **課題を書いたら、次の見出しはその答えにする**: 「課題：〜が見えない」→「改善後：〜が常に見える」のように、課題の言葉を受けて対にする。「できること」「機能」のような機能一覧の見出しより、前後の対比が伝わり、AI も問いと答えの組として引用しやすい
- **見出しの階層**: `##` → `###` → `####` の順に、飛ばさずに使う（`#` はページのタイトルなので本文では使わない）
- **1 段落 1 主張、一文で自立させる**: 「これ」「上記」「前述の」に頼らず、主語と対象を書く。AI は段落の一部だけを引用する
- **定義を書く**: 新しい用語は初出で「〇〇とは、〜のこと」と 1 文で定義する
- **比較・条件・手順は表か番号付きリストに**: 文章に埋めない
- **数字・固有名詞・バージョンを具体的に**: 「いくつかの」「最新の」ではなく「4 つのファイル」「Claude Code 2.1.325」
- **手順記事は**: 前提（環境・バージョン）→ 番号付きの手順 → 確認方法 → うまくいかないときの確認項目
- **最後にまとめ**: 要点を 3 行程度の箇条書きで。冒頭の `summary` と同じ文の繰り返しにはしない（冒頭は「得られるもの」、最後は「学び・判断の基準」）

## 3. 信頼性（E-E-A-T）

- 自分で試した結果・環境・日付を書く（「〜で動作を確認した」）。推測は推測と分かるように書く
- 一次情報（公式ドキュメント・リポジトリ）にリンクする。リンク文は「こちら」ではなく、リンク先の名前にする
- 早期アクセス版・仕様変更の可能性など、情報が古くなる条件を明記する
- 内容を更新したら `updated` を付け、本文の「〜時点」も直す

## 4. 画像・コード・リンク

- 画像は記事と同じ階層の `images/` に置き、`![代替テキスト](./images/xxx.png)` で参照する（ビルド時に webp に変換され、自サイトから配信される）。代替テキストは「何が・どこに・どう表示されているか」を 1 文で
- 画像に個人情報（実名以外のアカウント名・ホームディレクトリのパス・メールアドレス・社内の画面）が写っていないか確認する
- コードブロックには言語名を付ける（```` ```ts ````）。パスの個人名は `<ユーザー名>` のように置き換える
- 関連する自サイトの記事があれば本文中でリンクする（`/articles/<slug>/`）

## 5. 守ること（サイトのルール）

- `javascript:` などの危険なリンクを書かない
- 生の HTML は書いてよい（記事のみ）。ただし表示用に限る: `<details>`/`<summary>`（補足の折りたたみ）、`<kbd>`、`<figure>`/`<figcaption>`、`<mark>`、`<a>`、`<img>`（自サイトの画像。CSP で外部画像は表示されない）など
- 禁止: `<script>` `<iframe>` `<form>` `<style>` `<svg>` `<object>` `<embed>` `<meta>` `<link>` などの要素、`on〜` `style` `srcdoc` 属性、HTML 内の `javascript:`/`data:` URL（`scripts/security-scan.sh` が検出する。CSP でも動かない）
- 生の HTML の中は Markdown として解釈されないことがある。Markdown を書くときは、HTML のタグの前後に空行を入れる
- 構造（見出し・表・リスト）は HTML ではなく Markdown で書く。AI や検索エンジンが読み取りやすく、`llms-full.txt` にもそのまま載る
- ユーザーの個人情報（メールアドレス・ローカルのパスなど）を書かない
- ユーザーの体験談・感想を Claude が補ったときは、PR や返答でその箇所を伝えて確認してもらう

## 5.1 広告（アフィリエイトリンク）を入れるとき

Articles と Weekly Tech Note に入れられる（Weekly は AI の自動生成では入れさせず、人が確認するときに足す）。

- **リンクは ASP が発行した URL だけを Markdown のリンクにする**: `[商品名](https://af.moshimo.com/af/c/click?...)`。ASP は原則 **もしもアフィリエイト**（本は楽天・Amazon とも、もしもで作る）。もしものテキストリンク（`pl_id=616`）の `href` を使い、`//af.moshimo.com/...` のように `https:` がなければ付ける。「かんたんリンク」（`<script>` で表示するカード）はこのサイトでは表示されないので使わない。リンクの前に「PR」ラベルが CSS で自動で付く（景品表示法のステルスマーケティング規制への対応）。**PR を本文に手書きしない**（二重になる）
- 対応している ASP のドメインは `src/styles/global.css` の一覧（もしもアフィリエイト〔`af.moshimo.com`〕・A8.net〔`px.a8.net`・`rpx.a8.net`〕・楽天・バリューコマース・Amazon の短縮 URL）。**一覧にない ASP のリンクにはラベルが付かない**ので、新しい ASP を使うときは先にドメインを足す（`scripts/validate-weekly.mjs` の `AD_HOSTS` にも足し、リンク確認で広告リンクにアクセスしないようにする）。ビルド後に `npm run dev` でラベルが出ているか目で確認する
- リンクの文言は商品名・サービス名にする。「こちら」「詳しくはここ」のような文言にしない
- ASP の「商品リンク」（表・画像・価格付きの HTML）は使わず、`<a href="…">` の URL と商品名だけを取り出す
- ASP のコードに入っている `<img>`（計測用の 1×1 画像・バナー）や `<script>` は貼らない（CSP で外部の画像・スクリプトは表示されない。インプレッション数は計測されないが、クリックと成果は計測される）
- **効果を言い切らない（薬機法・健康増進法）**: 健康食品・サプリ・化粧品・健康器具などは「痩せる」「治る」「〇kg 減る」「肌が若返る」のように効果・効能を約束する書き方をしない。書けるのは「自分がこう使って、こうだった」という体験と、公式に表示されている事実まで
- 価格・キャンペーン・報酬条件は変わるので、日付を添えて書くか、「最新はリンク先で確認」と書く
- 実在しない ID・広告コード・試していない商品の体験談を書かない
- 自分のアフィリエイトリンクから自分で買わない・申し込まない（もしもの Amazon・楽天は本人購入が報酬の対象外。不正とみなされるおそれがある）。プレビューでの確認もリンクはクリックせず、リンク先の URL を見るだけにする
- 置き場所: Weekly は末尾の `## 関連書籍`、記事は末尾の `## 参考書籍` に 1〜2 冊。説明は書名・出版社の紹介から分かる事実だけにし、読んでいない本の感想を書かない

## 6. 確認

```bash
npm run build && bash scripts/security-scan.sh
```

ビルド後に、次を確認する。

- `dist/articles/<slug>/index.html` の `<title>`・`description`・`canonical`・`application/ld+json` が意図どおりか
- `dist/llms.txt` と `dist/sitemap.xml` に記事が載っているか
- `npm run dev` でスマホ幅・ダークモードの見た目（要点ボックス・表・FAQ）
